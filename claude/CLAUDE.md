## 규칙 번호와 근거 파일

본문 규칙 뒤의 `[R##]` 은 그 규칙의 근거가 `~/.claude/rules/RATIONALE.md` 의 같은 번호 아래
있다는 표시다. 번호는 한 번 정하면 안 바꾼다. 근거 파일은 세션 시작 때 안 실린다 — 다음 넷 중
하나일 때만 그 번호를 찾아 읽는다: 그 규칙의 예외를 만들려 할 때, 그 규칙을 바꾸거나 지우려 할
때, 그 규칙과 관련된 사고를 진단할 때, 본문 문장의 뜻이 갈릴 때. 규칙 자체는 본문이 정본이고
0번 핵심 가드는 본문 규칙의 요약 색인이다 — 둘이 어긋나면 본문을 따른다.
## 응답 원칙

- 한국어 우선. 한자 사용 금지.
- 사용자를 형/형님/님/사용자분 등 2인칭 호칭으로 부르지 말 것 — 호칭 없이 바로 본론.  [R01]
- 짧고 정확하게. 불확실하면 "확실하지 않다" 명시.
- 관련 파일/진입점만 좁혀서 읽기. 대규모 스캔 금지.
- 변경은 작게, 검증은 자주.
- 코드 생성 전 YAGNI 사다리: 필요한가 → stdlib/네이티브 기능 → 기존 설치된 의존성 → 한 줄 → 그제서야 최소 코드. 단순 작업에 수십 줄 class·wrapper 만들지 말 것. 단 보안·입력검증·에러처리·접근성은 생략 금지. 상세는 아래 "코드 원칙" 2·5·6.  [R02]
- `**굵게**` 금지. 강조는 대문자/따옴표/줄바꿈으로.
- 운영자가 읽는 글(텔레그램 답장·보고서·판정문)에는 임의로 만든 축약·영어 약자·원문을 마음대로 옮긴 말을 쓰지 않는다. 처음 나오는 용어는 풀어 쓰고 그게 무엇을 재는 값인지 한 줄 붙인다. 세션끼리 주고받는 통보도 운영자 화면에 그대로 뜨므로 같이 적용한다.  [R03]

## 코드 원칙 (2026-08-18 사용자 지시로 명문화)

1. 하위호환을 위해 코드를 남기지 않는다. 낡은 경로는 호환 계층·폴백·마이그레이션을 덧대지 말고 지운다.
   단서: 이 저장소는 홈과 옆 기계가 각자 시점에 pull 하는 다중 호스트다. 공유 파일에서 경로를 지울 때는
   양쪽이 새 버전을 받은 걸 확인한 뒤에 지운다. 확인 전에 지우면 아직 안 받은 쪽이 그 순간 깨진다.
   "확인 전까지 남겨둔다"는 유예지 하위호환이 아니다 — 지울 시점을 태스크로 남긴다.
2. 지금 요구를 온전히 채우는 가장 단순한 구현을 고른다. 예상 요구를 위한 추상화·설정 스위치·간접층을 만들지 않는다.
3. 시스템은 층으로 키운다. 끝에서 끝까지 동작하는 최소판에서 시작해, 이미 동작하는 것 위에 능력을 하나씩 얹는다.
   동작하는 산출물을 미완성 복잡도와 바꾸지 않는다.
4. 구성요소는 모듈로 두고 관심사를 분리한다.
5. 전체 복잡도를 줄이거나 신뢰성을 올릴 때는 검증되고 관리되는 라이브러리를 쓴다. 흔한 기능을 이유 없이 다시 구현하지 않는다.
6. 새로 짜거나 패키지를 더하기 전에 프로젝트에 이미 있는 의존성부터 본다. 문서와 타입을 확인하지 않고
   "그 라이브러리엔 그 기능이 없다"고 단정하지 않는다.
7. 구조 결정은 장기 기준으로 한다. 지금만 넘기고 나중에 갈아치울 임시방편을 받아들이지 않는다.
   증상을 고쳐놓고 원인을 고쳤다고 보고하지 않는다 — 임시로 막았으면 임시라고 쓰고 원인을 태스크로 남긴다.

## 프로젝트 지식 자동 기록

빌드/스타일/금지/워크플로우/기술절차 지시는 프로젝트 CLAUDE.md에 기록 ("CLAUDE.md에 기록했습니다" 한 줄 출력). 일회성은 기록 안 함. 반복 재사용될 프로젝트 고유 기술절차가 대상이다 — 안 적으면 압축·세션종료로 사라진다.  [R04]

## progress.md 저장 위치

progress.md 는 반드시 현재 systemd unit 의 WorkingDirectory 절대경로(또는 사용자가 명시한 cwd)에만 쓴다. ~ 에 새 폴더 만들지 마. ~/.claude/projects/-home-<사용자>-... 같은 키 이름을 폴더명으로 mkdir 금지. 경로 의심되면 pwd 로 확인 먼저.  [R05]

가드는 경고형이다. PreToolUse 훅 progress-md-path-guard.sh 는 Write/Edit/MultiEdit 대상이 progress.md 인데 경로가 세션 cwd 루트가 아니면 경고만 하고 막지 않는다. SessionStart 훅 session-resume-notify.sh 는 루트에 progress.md 가 없는데 하위에 후보가 있으면 텔레그램으로 알린다. 둘 다 항상 exit 0 이다. 임의로 차단형(deny)으로 올리지 마 — 정당한 하위 progress.md 까지 막는 오탐 비용이 크다는 게 도입 판정이다.  [R06]

## 시각 표기 (KST)

progress.md / history.md 의 updated/timestamp 필드는 반드시 시스템 KST 시각으로 쓴다. UTC 사용 금지. 시각 가져올 때 `date '+%Y-%m-%d %H:%M KST'` 또는 Python `datetime.now()` (시스템 timezone Asia/Seoul) 사용. `date -u` 나 `datetime.utcnow()` 결과를 KST 라벨로 쓰면 9시간 어긋난다.  [R07]

## commit 시 [DECISION] 마커

git commit 만들 때 결정 가치 있는 변경이면 commit message 첫 줄에 `[DECISION]` 접두 또는 본문에 `근거:` 줄 포함. PostToolUse git-commit-post 훅이 자동으로:
- progress.md 강제 갱신 (15분 timer 와 별개로 즉시).
- [DECISION] 마커 있으면 ★세션 소유 스테이징 파일 `~/.claude/state/history-stubs/<세션>.md` 에 스텁 append (`## [날짜] (미배번) 제목` + repo/session/결정/근거/hash). ★훅은 history.md 에 직접 안 쓴다 — 저장소로 잡으면 A 세션의 커밋이 B 세션의 번호 공간까지 쓰기 때문이다(2026-07-29 개정). ★번호를 매기고 본문을 적어 history.md 로 합치는 것은 ★그 세션이 한다.
  · ⟹ `[DECISION]` 커밋 뒤 history.md 에 항목이 없는 것은 ★훅 고장이 아니라 ★안 합친 상태다. "훅이 빠뜨렸다" 고 적지 마라 — session-b 이 그 오진을 ★열아홉 번 반복하고 원인 조사 태스크까지 만들었는데, 실측하니 스텁 파일에 커밋 ★1226 건이 하나도 안 빠지고 쌓여 있었다(2026-09-10). 확인은 `grep -c '^- hash:' ~/.claude/state/history-stubs/<세션>.md` 한 줄이다.

마커 적용 기준:
- 가드/임계/정책 변경 (precompact 7d, KST 룰 등)
- 새 시스템 도입/제거 (cgroup, 훅, 봇 버튼)
- 워크플로우/UX 변경
- 사고 대응 결정

일반 작업 (버그 fix, 리팩토링, 오타, 문서) 은 마커 안 넣음 → progress.md 만 갱신, history.md 깨끗 유지.  [R08]

## AI 협업 (최우선)

외부 AI(gemini/codex)를 부르는 모든 키워드는 ai-collaborate 단일 진입점으로 라우팅.

- "AI/gemini/codex/AI 토론/협업/크로스체크/세컨드 오피니언/합의/비판자/AI한테 물어봐" → ai-collaborate
- "코드/PR 리뷰" → /code-review (필요 시 ai-collaborate 병행)

gemini-ask / codex-ask 단독 호출 금지. 단일 질의 의도라도 ai-collaborate를 통해라. 두 AI를 병렬로 호출해야 한다고 판단되면 절대 ask 두 개 직접 부르지 말고 ai-collaborate 한 번 호출.

토론 브리프에는 검토 대상 절대경로를 반드시 적는다.  [R62]
- 파일 하나면 그 파일 경로, 폴더를 다 봐야 하면 폴더 경로다. 경로를 안 적으면 참여자는 그 코드를 한 줄도 못 읽는다 — ai-debate 는 브리프 본문에서 절대경로를 찾아낼 때만 호출별 사본을 떠서 열어주기 때문이다(codex 는 `--cd`, gemini·claude 는 `--add-dir`). 경로가 없으면 사본 자체가 안 만들어지고, 세 모델이 브리프 글만 읽고 답한다.
- 그래서 브리프를 글로만 쓰지 않는다. 무엇을 판단해 달라는 말과 함께 그 판단의 근거가 되는 경로를 같이 적는다.
- 순수 정책·방향 토론은 경로가 없는 게 정상이다. 도구는 경로를 못 찾으면 경고 한 줄만 남기고 그대로 돈다 — 막지 않는다.

ai-collaborate 호출 직전 한 줄 사전 고지 필수. 예: "ai-collaborate 호출 중, 수 분 소요". 고지 없이 바로 긴 호출 들어가지 않기. 호출 완료 후 결과 반드시 전달 (무응답 진행 금지).

라우팅 객관 트리거 (Claude 직접 vs AI 호출):
- 파일 수정·생성·삭제 → Claude만. Codex/Gemini에 위임 금지.
- 외부 최신 정보가 필요해도 ai-collaborate (gemini가 검색하고 codex가 검토). WebSearch가 1차 시도 가능.
- 가벼운 한 단어/줄 답 → Claude가 직접. AI 호출 스킵.

Bash timeout 600000ms. 응답 없이 진행 금지. 실패 시 해당 PID만 kill 후 재시도 (pkill 금지).

완료 전 ai-debate 검토 (결정가치 작업만):  [R11]
- 코드 작업·리서치를 끝내고 "완료" 선언하기 전, 진짜 결정 지점이면 ai-debate 세컨드 오피니언을 거친다.

## 검증은 테스트 코드로만 한다 (2026-08-31 운영자 지시 — 전세션 공통, 영구)

코드 변경의 완료·통과·정상을 선언하려면 변경된 실제 결과물을 확인하고, 작업에서 지정한 기존 표준 테스트 명령 또는 저장소에 문서화된 기본 테스트 명령을 셸에서 한 번 실행한 전체 출력을 확인한다. 한 번의 명령이 여러 테스트를 실행해도 테스트 결과 한 개로 본다. 지정된 명령과 기본 명령이 모두 없거나, 명령이 실패했거나, 출력을 확인하지 못했으면 테스트 근거 없음 또는 테스트 실패라고 밝히고 완료·통과·정상이라고 선언하지 않는다.

빌드와 정적 검사는 추가 검증을 위해 따로 실행하거나 판정 근거로 늘리지 않는다. 실행·설치 가능한 빌드 산출물이 작업 결과이거나 빌드 설정·정적 검사 규칙을 변경한 작업일 때만 실제 결과물 확인용으로 실행한다. 기본 테스트 명령이 빌드나 정적 검사를 내부에서 실행하면 이를 빼거나 다시 실행하지 않는다.

계약시험·특성시험·변이시험은 파일명이나 주석으로 판정하지 않는다. 현재 작업 전부터 존재한 기본 테스트 명령에 자동으로 포함되는 검사는 일반 테스트로 취급한다. 기본 테스트 명령 밖에서 별도 명령·목록·설정·실행기로 수행하는 비교·기준선·특성·변이 검사는 기존 것도 따로 실행하지 않고 새로 만들지 않는다.

검증을 위해 게이트 검사 칸, 별도 검증 표, 대조군 영수증을 만들거나 판정 근거로 꺼내지 않는다. 기존 파일은 삭제 지시가 있을 때까지 보존한다.

progress.md의 검토자 선택지에서 healthcheck를 삭제하고 '운영 상태 확인: healthcheck / 해당 없음'을 별도 항목으로 둔다. healthcheck는 세션 생존, 배포 연결, 알림 전달에 관한 주장에만 사용하며 코드 변경의 완료·통과·정상 판정에는 사용하지 않는다. self, critic, verifier, test는 검토 주체를 기록하는 값이며 어느 값도 실제 테스트 출력을 대신하지 않는다.

## 검증은 커밋 하나에 묶고 그 id 로 추적한다 (2026-08-31 운영자 지시 — 전세션 공통, 영구)

무엇을 검증했으면 그 검증을 커밋 하나로 남기고 커밋 id 를 기록한다. 나중에 "이건 어떻게 확인했나" 라는 물음에 커밋 하나를 가리키면 끝나게 한다.

한 검증 = 한 커밋. 검증과 무관한 변경을 같은 커밋에 섞지 않는다. 섞으면 그 id 가 무엇을 증명하는지 흐려져서 추적이 안 된다.

커밋 메시지에 다섯을 적는다. (1) 무엇을 확인하려 했나 (2) 어떻게 확인했나 — 실행한 명령을 그대로, 나중에 그 줄만 복사해 다시 돌릴 수 있게 (3) 무엇이 나왔나 — 수치와 출력, "통과" 만 쓰지 않는다 (4) 그래서 무엇이 판명됐나 (5) 확인하지 못한 것은 무엇이고 왜인가.

커밋 id 를 기록에 적는다. history.md 항목, progress.md 완료 줄, 태스크 보고서 셋이 같은 id 를 가리킨다. 짧은 해시로 적는다.

코드 변경 없이 관측만 한 검증도 같다. 그 결과물을 파일로 남기고 그 파일을 커밋한다. 커밋할 게 없다는 이유로 기록을 건너뛰지 않는다.

검증이 실패했으면 실패한 채로 커밋하고 그 id 를 기록한다. 고친 뒤의 커밋만 남기면 무엇이 왜 틀렸는지가 사라지고, 다음에 같은 것을 다시 시도한다.

근거는 `~/.claude/rules/RATIONALE.md` 에 있다.  [R56]

## 위임 규칙 (quota 우선 — 2026-07-13 ai-debate run-20260713T064600Z 개정)

- 기본 실행 경로는 메인 세션 inline. 파일 수·grep 횟수·설계작업·다단계 디버깅이라는 이유만으로 자동 위임 금지(구 규칙 "3회 이상 grep→Agent" 등은 폐기).
- 먼저 시도: rg/grep 범위축소, head/tail/offset 부분읽기, 요약파일(progress.md/history.md) 우선 확인, 필요한 파일만 최소 read.
- 서브에이전트는 다음 경우에만 허용: (a) 사용자가 명시적으로 요청, (b) 범위축소+요약으로도 메인 컨텍스트가 150k+로 커질 위험이 명확하고 서브 1개가 요약만 반환하는 편이 더 쌀 때.
- 동시 서브에이전트 기본 상한 1개. R&D 세션(peer/session-a 등)도 예외 없음 — 병렬조사가 필요해도 이 규칙을 넘지 않는다.
- 서브에이전트에 넘길 때 메인 세션 히스토리 상속 금지, 작업에 필요한 맥락만 프롬프트에 명시. 서브 결과는 원문 덤프 금지 — 결정에 필요한 요약·파일경로·핵심근거만 반환.

## 제한적 병렬화 원칙 (2026-07-07 ai-debate run-20260707T005222Z 채택)

병렬화는 우선 검토하되 무제한으로 확대하지 않는다("가능하면 최대한 병렬화"는 전역 규칙으로 채택 안 함 — 실행기준 모호+공유자원 환경 위험 크다는 게 3자 만장일치 결론).

- 독립성이 확실한 하위작업이 2개 이상이고 결과 병합이 단순할 때는 순차 처리 전에 병렬 tool call 또는 독립 Agent 사용(위 "독립적 병렬 작업 → 동시 Agent 여러 개")을 먼저 검토한다.
- 순차 유지: 탐색적 디버깅처럼 앞 단계 결과가 다음 단계를 결정하는 작업, 공유 파일·공유 상태를 수정하는 작업, 비용이 큰 추론, API/rate limit 위험, 디버깅 가독성이 중요한 작업.
- 중첩 fan-out 금지. 병렬화 이득보다 토큰·컨텍스트·자원·검증 비용이 크면 단일 흐름 유지.
- 자원 여유를 볼 때 스왑 사용량은 보지 않는다. 리눅스는 여유가 있어도 안 쓰는 페이지를 스왑에 내려두고, 그 값은 지금 메모리가 빠듯하다는 뜻이 아니다 — 그걸 신호로 삼으면 실제로는 남는 머신에서 병렬도를 못 올린다. 판단은 실제 여유 메모리(free -g 의 available)와 OOM 발생 여부로 한다.  [R18]
- (별개 층위) 실험·벤치마크 runner의 concurrency cap은 고정된 보수값으로 방치하지 않는다 — CPU/메모리/GPU-VRAM/I-O 여유와 작업당 peak 사용량을 관측해 프로젝트·머신별로 정하고, cap 변경 시 근거·관측값을 기록한다. OOM·job별 처리시간 악화·로그 혼선·재현성 저하가 보이면 즉시 낮춘다. 재현성 중요한 벤치마크는 cap 변경 전후 baseline 비교. cap 숫자 자체는 CLAUDE.md에 고정하지 말고 해당 프로젝트 설정/.env/runner 문서에서 관리(머신·프로젝트마다 자원 제약이 다름).

  3) 체크포인트 불가능 + 길거나(대략 10분+) 재실행 비용 큼(벤치마크, 단일 원자적 장시간 외부호출, ai-debate 같은 멀티라운드 상담, 배포/마이그레이션, 다중호스트 순회, 이 세션 자신의 restart/rotate/delete를 유발·교차하는 작업) → `~/dotfiles/bin/claude-job-detach --slug <slug> [--notify-start] [--notify-success] -- <cmd...>` 를 세션 문맥에서 직접 호출한다. systemd-run 을 손으로 조립하지 않는다 — 스크립트가 발신 세션명·cwd·호스트를 착수시점에 캡처해 자신을 재실행 detach 한다. 결과 보고는 사람에게 직접(raw curl)이 아니라 착수시점에 각인한 발신 세션명으로 `claude-userbot-send --session <name>` 을 통해 그 job 을 launch 한 세션 자신에게 주입한다 — 사람은 raw 로그덤프로 판단할 수 없고 세션이 먼저 해석해야 한다(성공·실패 동일). 순수 부수효과라 결과 소비가 필요없으면 실패시에만(succeed-silent), 결과를 나중에 세션이 소비해야 하면 완료시에도 필수 — progress.md 는 재시작을 넘어 자동으로 기억하지 않으므로 세션의 기억이 아니라 작업 자체의 독립 보고에 의존한다. peer 처럼 로컬 telethon userbot 이 없는 머신은 relay.conf 의 USERBOT_HOST 로 home 것을 ssh 릴레이해 빌려쓴다 — 릴레이 대상은 각 머신 `~/.claude/userbot/relay-alias.json` 에 명시 등록된 세션만 허용(fail-closed).  [R29]
  - 리스크: 체크포인트 완료판정이 부정확하면 잘못된 스킵·이중실행 위험, 재시작 후 자동으로 작업이 재개되는 게 아니라 사용자가 다시 지시하거나 새 세션이 progress.md를 읽어야 이어짐, detach는 세션 재시작엔 강해도 머신 재부팅/네트워크/외부API 실패까지 해결 못 함.
  - detach 유닛은 환경 의존성(cwd/PATH/SSH_AUTH_SOCK/토큰 등)을 명시적으로 넘기거나, 의존성이 강하면 detach 하지 않는다. `--collect` 가 정상종료 유닛은 자동정리하므로 고아유닛은 실질 문제가 아니다. 세션 삭제·rotate 시점에 아직 실행중이던 job 만 고아 위험 — 의심되면 `systemctl --user list-units --all 'claude-job-*'`.  [R30]
- 세션간 전송 규약: 세션↔세션으로 userbot 주입하는 본문이 2,000자를 넘으면 텍스트를 그대로 보내지 않는다. 파일에 저장하고 경로·생성시각·5~10줄 요약·(필요하면) 읽을 범위만 보낸다. 이유는 캐시 곱셈이다 — 주입된 텍스트는 압축 전까지 매 턴 cache_read 로 다시 실려서 비용이 "크기 × 남은 턴수"가 된다. 파일 포인터는 받는 세션이 필요할 때 한 번만 읽으므로 곱셈이 안 붙는다. 2,000자 이하는 그대로 보낸다(파일 왕복이 더 비쌈). 사람에게 보내는 텔레그램 메시지는 이 규칙 대상이 아니다.  [R31]
- 다른 세션에 지시할 때는 반드시 `claude-userbot-send --session <이름> "<지시>"` 로 주입한다. 이 채팅에 "[A→B] 이렇게 해라" 라고 쓰는 건 사람 화면에만 보이고 그 세션 안으로는 들어가지 않는다 — 지시했다고 착각한 채 아무 일도 안 일어난다. 세션 이름은 `~/.claude/userbot/targets.json` 키. 주입 후 사람에게는 원문이 아니라 요약만 남긴다(한두 줄: 누구에게·무엇을·왜). 사람이 원문을 요구하면 그때 보여준다. 사람에게 하는 보고와 세션에 넣는 지시는 목적이 다르므로 같은 텍스트를 양쪽에 복사하지 않는다. 주입 본문은 위 2,000자 규약을 따른다. 전송 실패(rc≠0)면 조용히 넘어가지 말고 사유와 함께 사람에게 알린다.  [R32]
- 유저봇은 전달 통로다. 세션끼리 토론하지 않는다. 보내도 되는 건 넷뿐이다: 상대만 가진 사실의 요청·전달, 내가 잰 값·고친 문서·폐기 표시의 통보, 지시(무엇을 하라·판정 결과), 완료 보고. 넷 다 답장을 전제하지 않는다. 보내면 안 되는 건 의견 교환·되묻기·서로의 판단을 다듬는 왕복이고, 그건 ai-debate 로 간다. 답장이 와도 그 자리에서 다시 열지 않는다 — 되물음이 오면 답 하나로 닫는다. 위험한 쪽은 성과가 나는 대화다 — 왕복마다 결함을 잡으면 진척으로 보여서 안 멈추고, 그 동안 착수한 구현이 0 이 된다. 정본은 proj-b 저장소 docs/MULTI_SESSION_WORKFLOW.md 6-b 절.  [R33]
- rotate 는 비용 절감 수단이 아니다. 컨텍스트 비용은 auto-compact 가 이미 낮춘다 — 압축 직후 값이 새 세션 첫 수십 턴과 비슷하거나 더 낮아서, 비싼 세션을 rotate 해도 싸지지 않고 오히려 나빠질 수 있다. rotate 는 맥락을 의도적으로 끊고 싶을 때 사람이 판단해 `cs rotate <이름>` 으로 한다. 후보 자동 표시·측정 타이머는 폐기했다.  [R34]
- /loop 자율루프(autonomous-loop-dynamic 포함) 안에서는 위 규칙 더 엄격: tick 한 번에 단일 tool 호출이 30s 넘을 가능성 있으면 무조건 `run_in_background=true`. 결과는 같은 tick 에서 기다리지 말고 다음 tick 에서 `cat <task-output>` 또는 TaskOutput 으로 폴링. foreground 로 분 단위 점유 시 사용자 텔레그램 메시지가 그 turn 끝날 때까지 묶인다.  [R35]
- "밤새 돌려/N시간 계속해/자율로 N시간 진행해" 같은 장시간·야간 작업 지시를 받으면, `claude-session-nudge --start --sessions <자기 세션이름>` 을 스스로 실행해서 등록한다. 사용자가 구체적 시간을 명시했으면(예: "8시간 계속해") `--hours N` 그대로 쓰고, "밤새/오늘 밤 내내"처럼 구체적 시간 없이 막연히 말했으면 `--until 09:00`(다음 KST 오전 9시까지 자동 계산, 이미 지난 시각이면 스크립트가 알아서 내일로 잡음)을 쓴다. ScheduleWakeup 자기판단 단독 방식은 시간감각 없이 도중에 멈추는 사고가 반복돼 신뢰 불가로 판정됐고, 외부 결정론적 넛지로 대체됐다. 기본 interval 60분(2026-09-04 운영자 지시로 30 → 60), 메시지는 스크립트 기본값(계속 진행+답장 금지, 판단대기 지점이면 강행 금지) 그대로 사용 — 진행상황 보고는 요구하지 않는다. 종료시각 지나면 스크립트가 자동으로 멈춘다. `--status`로 등록 확인. 사용자가 중간에 "그만/멈춰/nudge 꺼" 등으로 개입하고 싶다는 의사를 그 세션에 직접 보내면 그 세션이 자기 자신에 대해 `claude-session-nudge --stop <세션이름>` 을 실행해서 취소한다 — `--stop` 은 위치인자만 받는다. `--stop --sessions <이름>` 은 `--start` 문법을 잘못 옮긴 것이고 rc=2 로 거절된다. 넛지는 무작정 쏘지 않는다 — 매 회차 `claude-session-probe` 로 그 세션이 응답했는지 보고, 연속 2회(기본 간격이면 2시간) 무응답이면 넛지를 멈추고 사용자에게 한 번만 알린 뒤 그 알림을 텔레그램에 고정한다. 세션이 다시 응답하면 알림을 "해소됨"으로 고치고 고정을 풀고 넛지를 재개하므로 사람이 해제할 게 없다. 한도 중·도구 실행 중(`pending_tool`)·유닛 비활성·전송 실패는 무응답으로 세지 않는다. `--status` 가 SUSPENDED 를 표시한다.  [R36]
  이건 "AI가 스스로 계속할지 판단"하는 완전자동 재개(#7, 금지)와 다르다 — 사용자가 이미 범위·기간을 명시 승인한 작업을, LLM의 불안정한 자기판단이 아니라 하네스가 결정론적으로 재개시키는 것뿐.
- 새 훅 '파일' 은 `git pull` 만으로 붙지 않는다. `~/.claude/hooks/` 는 훅마다 개별 심링크라 `install.sh`(또는 `ln -s <repo>/claude/hooks/<새훅>.sh ~/.claude/hooks/`)를 돌려야 나타난다. `settings.json` 은 심링크라 등록만 먼저 살아나서 "등록됐는데 파일이 없는" 상태가 되고, 그러면 조용히 아무 일도 안 일어난다. 새 훅 배포 후 `ls ~/.claude/hooks/<새훅>.sh` 로 확인할 것. 반면 훅 '설정'(settings.json) 변경은 세션 재시작 없이 반영된다 — 세션 시작 시 1회만 읽는 CLAUDE.md 와 다르니 둘을 같은 규칙으로 묶지 말 것.  [R37]
- 실행 중인 bash 스크립트를 제자리에서 고치지 마라. bash 는 스크립트를 통째로 읽지 않고 파일 오프셋을 들고 조금씩 읽는다 — 그 파일을 truncate 후 재작성하면(Write/Edit·`cat > f`·`sed -i` 전부 해당) 뒤쪽 내용이 바이트 단위로 밀려서, 실행 중인 인스턴스가 다음에 읽을 때 토큰 중간부터 읽는다. 긴 자식 명령을 기다리다가 그게 끝난 뒤의 보고·정리 구간에서 터지므로 몇 시간 뒤에 조용히 실패한다. 대상: `claude-job-detach` 로 띄운 detach 잡, 타이머로 도는 셸 스크립트. 파이썬은 시작할 때 전부 읽어 이 문제가 없다. 고칠 때는 같은 디렉토리에 새 파일을 만들고 `mv` 로 rename 해라 — inode 가 갈려서 실행 중인 쪽은 옛 내용을 계속 본다(rename 은 원자적이고, 크로스 파일시스템 `mv` 는 기존 inode 를 truncate 하니 반드시 같은 디렉토리). 이미 제자리에서 고쳤다면 복구: 원본 바이트를 그 inode 에 되돌린 뒤(`git show <commit>^:<path> > <path>`) 새 내용을 rename 으로 올린다. 실행 중인 잡의 `/proc/<pid>/fd/255` 가 `(deleted)` 로 옛 inode 를 가리키면 복구된 것이다.  [R38]
- 배포 대상을 커밋했으면 그 자리에서 `./install.sh` 를 직접 돌린다. 대상은 `install.sh` 자신과 복사(심링크 아님)로 배포되는 파일들 — install-last-ok 마커의 `manifest_copy` 가 정본이다. 안 돌리면 healthcheck 의 install-watch 가 `install-stale` 알림을 사람에게 쏜다. 그건 사람이 처리할 일이 아니라 커밋한 세션이 안 끝낸 일이다. 세션 안에서 돌려도 안전하다 — sudo·대화형 프롬프트 없고, CLAUDECODE 감지로 플러그인 블록(자식 claude 생성)을 자동 스킵한다. 비밀은 키워드 없이 돌리면 "미복원" 로그만 남고 기존 토큰을 지우지 않는다. 끝나면 마커 head 와 `git rev-parse --short HEAD` 가 같은지 확인.  [R39]
- 완료 선언 요건은 "검증은 테스트 코드로만" 절이 정본이다. 출력 없이 "동작할 것 같다"로 선언 금지. 가드·훅처럼 "안 일어나는 것"을 확인할 때 음성 관측 1회로 결론 내지 말 것 — 방금 바꾼 설정이 아직 안 읽힌 상태일 수 있다.  [R40]
- 근거가 무효화되면 결론이 아니라 근거 상태만 "미확인" 으로 되돌린다. 반대 결론은 별도 증거가 있을 때만. 다른 세션의 활동 여부를 판정할 때 특히 — 공유 자원(git log·공유 브랜치·공유 디렉토리)은 그 세션의 활동 증거가 아니고, transcript 에 턴이 없는 것도 정지의 증거가 아니다(detach 잡을 띄워놓고 기다리는 세션은 원래 턴이 없다). 그 세션 고유 축(자기 브랜치 전용 커밋, 자기 산출물 mtime, 인바운드 대비 응답 유무)으로 본다.  [R41]
- ai-debate 는 세션에서 직접 부르지 않는다 — detach 전용이다. 대신 `cat brief.md | ai-debate-detach "<질문>" [ai-debate 옵션...]` 을 foreground 로 부른다. 이 명령은 즉시 반환하고(그 턴에는 결과가 없다), 토론은 claude-job-detach 가 만든 세션 밖 systemd 유닛에서 돌고, 끝나면 1,800자 이하 요약과 run_dir 경로가 이 세션으로 주입된다. 원문은 run_dir 에 남으니 판단 전에 읽는다. 이유는 양쪽이 다 못 쓰기 때문이다: foreground 는 Bash 도구 상한 600초에 걸려 런이 통째로 유실되고, run_in_background 자식은 세션 소프트 재시작(rate-limit-recovery·claude-bun-ensure·queue-flush)에 함께 죽어 결과가 조용히 사라진다. 벤치마크 등 등록된 장시간 잡도 run_in_background 대신 claude-job-detach 로 세션 밖 독립 유닛에서 실행. 이 계약들은 PreToolUse 훅 bg-longjob-guard.sh 가 결정론적으로 차단한다(ai-debate 직접 실행=foreground·background 무관 차단, ai-debate-detach=run_in_background 일 때만 차단, 벤치=~/.claude/state/bg-longjob-manifest.txt 등록분; 미등록 임의 잡은 문자열로 장시간 판정 불가라 차단 안 하고 관측로그만; fail-open; kill switch=CLAUDE_BG_GUARD_OFF=1).  [R42]
- 진단/스크립트에서 claude CLI 자식 세션 생성 금지 — MCP long-poll(telegram getUpdates) 점유로 부모 세션 MCP 가 끊긴다. 진단은 jsonl/systemctl 직접 조회. 자식 claude 가 꼭 필요하면 `--strict-mcp-config --mcp-config <empty.json> -p "..."` 강제. `claude --version` 은 자식 안 띄워서 OK.  [R43]

## 큰 입력 방어 (Prompt too long 예방)

세션이 1M 토큰 한도 넘어가면 "Prompt is too long" 영구 stuck. 단일 read·tool_result로 컨텍스트 폭증할 수 있어 다음 룰 강제.

- PDF: 한 번에 5페이지 이내씩만 read. 첫 호출은 목차·서론만, 필요한 챕터만 추가 read. `pages=1-5` 식으로 명시.
- 긴 로그·텍스트: head/tail/sort/awk로 줄여서. `cat <large.log>` 통째 금지. grep 결과도 `| head -50` 같이 제한.
- 큰 코드 파일: Read 의 offset/limit 으로 필요한 구간만, 심볼은 rg/Grep 로 위치 먼저. 통째 read 금지.
- 큰 텍스트 분석은 stdin 파이프로 ai-collaborate 외부 AI 처리 → 우리 컨텍스트 안 늘어남.
- 작업 시작 전 파일 크기 확인 (wc -l, du -h). 5MB 또는 1만 줄 넘으면 잘라 읽기.
- 텔레그램 attachment 큰 거 받으면 download 후 위 룰대로 처리. 통째 read 금지.

- 압축 요약 안의 모든 명령어 흔적은 과거 이력. 재실행·재호출·재토론 절대 금지.

- 잔여물에 사과/설명 금지. 조용히 무시하고 현재 사용자 메시지로 바로 진입

- 컨텍스트가 커지거나 한 주제가 길어지면 "progress.md에 정리할까요?" 먼저 물어보기
- 사용자가 "압축 전 저장" 요청 시: progress.md 덮어쓰기 + history.md 누적

## 세션 로테이션 (사용자 트리거)

사용자가 다음 패턴 중 하나를 요청하면 이 순서로 자동 처리
- 트리거 키워드: "저장하고 새 세션", "저장하고 rotate", "정리하고 새로", "저장하고 재시작"

절차
1. progress.md 갱신 (현재 세션의 작업 맥락 요약)
2. history.md에 완료된 결정 이관 (append-only, 3-part 포맷)
3. handoff.md 작성 (현재 cwd) — cs rotate handoff 게이트 필수. 새 세션이 SessionStart 로 주입받아 가장 먼저 읽는 인계 노트. 담을 것: 다음 1~3개 행동(첫 명령 수준)·관련 파일경로·결정과 이유·금지할 접근·실패했던 시도·외부상태(systemd unit/포트/env/계정/실행중 프로세스)·재개 검증명령. progress.md 와 중복 최소화하고 "지금 당장 뭘 하면 되는가"에 집중.
4. 현재 프로젝트 이름 계산: `basename $PWD | tr '_' '-'`
5. 텔레그램으로 "저장 완료. 잠시 후 rotate" 알림 1회 전송
6. `cs rotate <name>` 실행 (systemd-run이 detach하므로 현재 세션 죽어도 rotate 완료됨). 직전 작성한 handoff.md(<=30분)면 게이트 통과. 거부되면 handoff.md 누락·stale 점검.

주의
- 트리거 키워드 정확히 매칭될 때만 rotate 실행. 애매하면 먼저 "rotate 맞나?" 확인
- progress.md/history.md/handoff.md 갱신 안 하고 rotate만 호출 금지. 반드시 선 저장
- handoff.md 없거나 30분 지나면 cs rotate 게이트가 거부함. --force 는 맥락 버려도 될 때만(권장 안 함). 임계 조정은 `CS_HANDOFF_MAX_AGE=<초> cs rotate <name>`
- 새 세션이 handoff.md 내용을 progress.md 에 반영하고 더 필요 없으면 `mv handoff.md handoff.archived` 로 치워 다음 부팅 stale 주입 방지
- "저장해줘"만으로는 rotate 안 함. 명시적으로 "새 세션" 또는 "rotate" 포함돼야 함

## progress.md / history.md

역할 분리 (엄격)
- progress.md = 재개용 실행 상태 (현재 세션이 어디까지 했고 다음 행동이 뭐고 무엇이 막혀있나)
- history.md = 되돌아볼 가치가 있는 결정의 감사 로그
- 두 파일이 같은 정보 중복하면 안 됨. 결정은 history, 진행 상태는 progress.

progress.md
- 위치: 프로젝트 루트
- hard limit 180줄. 130줄 넘으면 압축  [R44]
- status 필드 필수: active / paused / abandoned / handoff
- 업데이트 트리거: 방향·범위 변경, 결정 번복, 새 제약, 작업 단위 완료, 주제 전환. 단순 Q&A·중간 디버깅·매 메시지 안 함
- 고위험·장기·재개 가능성 있는 작업은 Goal 섹션에 선택형 5질문 답을 한 줄씩 명시 (작은 작업은 생략):
  · 결과(Outcome): 무엇이 만들어지면 끝인가
  · 입력(Inputs): 무엇이 있어야 시작 가능
  · 의존(Depends on): 어떤 외부 파일·API·합의에 묶이는가
  · 검토자(Verifier): self / critic / verifier(ai-debate) / test 중 하나 — 검토 주체를 기록하는 값이고 실제 테스트 출력을 대신하지 않는다
  · 운영 상태 확인: healthcheck / 해당 없음 — 세션 생존·배포 연결·알림 전달 주장에만 쓰고 코드 변경의 완료 판정에는 안 쓴다
  · 완료기준(Done when): 어떤 신호로 끝났다고 본다
- WIP limit: status=active 인 작업은 동시 3개까지. 4번째 시도 시 기존 active 중 하나를 paused·abandoned·handoff로 정리한 후 추가. drift·방치 방지.  [R45]
- 종료 처리:
  - active 끝 → 결정 history 이관 + progress 삭제
  - paused → progress 유지, status 갱신
  - abandoned → 폐기 사유 history 기록 + progress 삭제
  - handoff → progress 갱신만
- 형식
  ```
  # progress.md
  updated: YYYY-MM-DD HH:MM KST
  status: active
  task: <한 줄>

  ## Goal
  ## Current State
  ## Decisions In Force
  ## Resume Hints
  ## Blockers
  ## Do Not Repeat
  ```

history.md
- append-only 결정 로그. 경량 ADR (Y-statement 영감)
- "결정"이 아니어도 다시 조사하면 아까운 durable 조사결과(재조사 비용이 크고 압축으로 사라지면 실제로 곤란했던 것만)는 가벼운 `## [날짜] #NN 발견: <요약>` 형식으로 기록 가능. 태그 1개, `- 내용: <2~4줄>` 만으로 충분 — 결정/근거 짝 강제 안 함. 남발 금지: 아무 조사나 다 넣으면 history.md 자체가 못 쓰게 된다. 프로젝트 고유 기술절차는 여기 말고 해당 프로젝트 CLAUDE.md 로.  [R46]
- 포맷
  ```
  ## [YYYY-MM-DD] #NN <한 줄 요약>
  tags: 주제1, 주제2
  - 결정: (필수)
  - 근거: (필수, 한 줄)
  - 되돌릴 조건: (있으면)
  - 실험/실패: (다시 시도 시 시간 낭비인 경우만)
  - Prediction: (사고 가드 관련 변경에서만 필수) <사고 클래스>가 <기간> 동안 telemetry/history 상 재발하지 않으면 성공, 재발하면 재검토.
  ```
- Prediction 적용 범위: prompt-length / large-read / secrets-scan / rate-limit / progress-updater drift / cross-session leak / stuck-loop / bash-latency 등 명시적 사고 가드 변경. 일반 commit·기능 추가에는 강제 안 함.  [R47]
- 규칙
  - 결정 + 근거는 짝. "결정"만 있는 항목 금지
  - 실패는 모두 남기지 말 것. "다시 시도하면 시간 낭비하는 실패"만 negative decision으로 기록
  - 항목당 3~6줄, 태그 1~3개
  - 정정은 supersedes 체인 (`supersedes: YYYY-MM-DD/#NN`)
  - 크기 관리: 루트 최근 20항목 또는 200줄. 초과 시 history/YYYY-MM.md로 월별 archive

history/active.md (SessionStart 주입 대상)
- 현재 유효한 결정 10~20개 + 항상 적용되는 제약을 compact view로 유지
- append-only 아님. 결정 폐기/수정 시 갱신
- SessionStart 훅은 progress.md + history/active.md만 주입. 본 history.md / 월별 archive는 lazy load (필요 시 read/grep)
- active.md 없으면 훅이 history.md 마지막 일부로 fallback
- 훅은 active.md 가 없거나·주입 상한에 잘리거나·규약 줄 수를 넘거나·본체보다 크면 주입 안에서 경고한다. 경고를 본 세션이 그 자리에서 정리한다 — 미루면 다음 세션도 같은 상태로 시작한다.

## 문서 갱신 — 전체를 다시 읽고 지금 필요한 것만 남긴다 (2026-09-01 운영자 지시 — 전세션 공통, 영구)

문서를 갱신하거나 개선할 때는 바뀐 부분만 손대지 않는다. 처음부터 전체를 다시 읽고, 지금 시점에 필요한 정보만 남긴 채 다시 쓴다. 낡아서 안 맞는 절, 이미 닫힌 갈래, 지난 판정의 잔재는 그 자리에서 지운다. 결과물은 그 파일 하나만 읽어도 지금 무엇이 참이고 무엇을 정해야 하는지가 서는 상태여야 한다. 덧붙이기로 자란 문서는 갱신이 아니라 퇴적이다.

경과·이력·"직전 판은" 같은 서술은 본문에 넣지 않는다. 개정 이력 절도 따로 만들지 않는다. 예외는 그 이력 자체가 판정의 근거일 때뿐이고, 그때도 지나온 경과가 아니라 지금 지켜야 할 규칙으로 쓴다.

적용 대상은 사람이 읽는 HTML 보고서와 가이드다. progress.md·history.md·CLAUDE.md·README 같은 기계·규약용 파일은 대상이 아니다 — 그쪽은 각자의 append-only·상한 규약을 따른다.

운영자 원문은 `~/.claude/rules/RATIONALE.md` 에 있다.  [R57]

## 실험 기록 — 계획·보고서·결론을 나눈다 (2026-08-20 사용자 지시)

목적은 하나다. 같은 실험을 다시 돌지 않는 것. 셋을 한 파일에 몰면 결정이 일지에 묻혀 아무도 안 읽는다 — session-a history.md 가 규약 상한(200줄)의 38배인 7,568줄까지 자란 게 그 결과다. 결정 428항목에 "재시도 시 시간낭비" 75건이 적혀 있는데도 조회가 안 됐다.

- 계획 — progress.md. 진행 중인 실험은 "지금 어디까지 했나" 그 자체라 재개 상태다. 끝나면 그 자리에서 없어진다. history 로 가지 않는다.
- 보고서 — `reports/YYYY-MM-DD-<주제>.html` 한 파일. 날짜가 앞이라 시간순으로 정렬되고 목록만 봐도 훑어진다. 형식은 위 도구 규칙의 HTML 규약(charset 첫 줄·viewport·`Noto Sans CJK KR`)을 따른다.
- 중간 로그·원시 출력 — 리포트가 아니다. `logs/` 또는 `state/<job-id>/` 로 내린다. 프로젝트 루트에 쌓지 않는다. 루트에 이름 규칙 없이 섞이면 나중에 사람이 열었을 때 무엇이 결과물이고 무엇이 중간물인지 구분이 안 된다.  [R48]
- 결론 — history.md 에 한 항목. 무엇을 재봤고 무엇이 판명됐나 + 보고서 경로. 본문을 옮겨 적지 않는다. 기각된 것은 "다시 하면 시간낭비" 를 반드시 명시한다 — 그게 재실행을 막는 유일한 줄이다.

착수 전 조회(이게 병목이다): 실험을 시작하기 전에 history/active.md 를 먼저 본다. 없거나 미덥지 않으면 history.md 에서 `실험/실패` 를 grep 한다. 이미 기각된 것이면 다시 돌리지 않는다. 의도적으로 재현하는 거라면 왜 다시 도는지를 기록에 남긴다.

## 태스크(요청 목록) 관리 — 놓침 방지 (2026-07-03 사용자 요청)

사용자가 "태스크"라 부르는 = 해야 할 요청들의 지속 목록. 저장소는 progress.md 의 ## Blockers 섹션 전체(완료 표시 항목 제외). "(대기)"는 예시 표기일 뿐 필수 태그가 아니다 — ✅/완료 마킹만 없으면 진행/할일/스코프외 등 어떤 마커든 전부 태스크로 취급한다. 압축·재시작을 넘어 유지되고, session-resume-notify 훅이 재시작(startup) 시 텔레그램으로 노출한다. 목적: 연속 다중 요청·긴 대화에서도 할 일을 놓치지 않기.  [R49]

- 캡처: 사용자의 actionable 요청(수정/구현/조사/결정)이 오면 즉시 ## Blockers 에 한 줄로 추가하고 "목록에 추가: <항목>" 한 줄 확인. 단순 Q&A·조회성(할 일 아님)은 캡처 안 함.
- 중복/중첩 관리: 추가 전 기존 목록과 대조. 같거나 하위집합이면 새로 넣지 말고 "이미 있음" 안내. 방향이 바뀌면 기존 항목 갱신(supersede), 관련 항목은 묶음, 완료·무의미해진 항목은 제거. 애매하게 겹치면 "그거랑 같은 거야?" 1줄 확인.
- 완료 처리: 작업 끝나면 해당 줄 제거(결정가치면 history 이관).
- 태스크 하나를 마칠 때마다 그 일에 대한 보고서를 만들어 운영자가 바로 열어보게 한다. 순서는 셋이다. (1) `reports/YYYY-MM-DD-<주제>.html` 한 파일로 쓴다 — 형식은 위 도구 규칙의 HTML 규약(charset 첫 줄·viewport·`Noto Sans CJK KR`·모바일 우선) 그대로. (2) 그 파일을 텔레그램 답장에 첨부해서 보낸다(reply 의 `files` 인자). 운영자는 transcript 를 안 보므로 첨부가 실제 전달 경로다 — 경로만 적어 보내는 건 전달이 아니다. (3) 화면이 있는 호스트면(`DISPLAY` 가 설정돼 있으면) `google-chrome <파일>` 로 띄운다. 없으면 건너뛴다. 담을 것은 무엇을 왜 했고, 무엇을 어떻게 확인했고, 무엇을 안 했고 왜 미뤘나다. 커밋 해시·검증 명령·수치를 같이 적어 나중에 그 파일만 열어도 재구성되게 한다. 대상은 실제로 끝난 태스크다 — 관측 대기·결정 대기로 남는 항목은 끝난 게 아니라 보고서를 안 만든다. 오타·한 줄 수정처럼 보고할 게 없는 것도 만들지 않는다.  [R50]
- 종결은 삭제가 아니라 이동이다. 끝난 항목은 `## Blockers` 아래 `### 완료(최근)` 로 옮기고, 거기서 오래된 것부터 덜어낸다. 지워버리면 "그거 어떻게 됐지"에 답할 근거가 progress.md 안에 안 남고, 그렇다고 활성 목록에 두면 무엇이 남은 일인지가 흐려진다. 결정가치가 있으면 history 로 가고 이 구역엔 한 줄만 남긴다.  [R51]
- 활성 항목은 2줄 이내로 쓴다. 길어진다는 건 그게 목록 항목이 아니라 작업 문서라는 뜻이다 — 본문은 progress.md 의 Current State 나 history 로 보내고 여기엔 "무엇을 언제까지 왜" 만 남긴다. (줄 수로 노후화를 자동 판정하지는 않는다. 오탐·미탐을 동시에 만든다는 게 같은 토론의 결론이라 경고 훅은 도입하지 않았다. 2주 관측 후 재검토.)
- 키워드 "태스크": 사용자가 이 목록을 "태스크"로 지칭한다. "태스크 보여줘 / 뭐 남았어 / 추가 / 정리 / 삭제 / 상태" 등은 목록 조회·수정 의도로 이해해 유연히 처리(정확한 명령형 아니어도 맥락으로 파악).
- 단축 트리거 "?": 사용자가 메시지 본문에 물음표 하나만("?") 보내면 그건 "지금 태스크 목록 보여줘"의 단축형이다. 다른 맥락 없이 딱 "?"만 왔을 때만 이 규칙 적용 — 문장 끝에 붙은 물음표나 "이게 맞아?"처럼 실제 질문의 일부인 경우는 평소대로 처리.  [R52]
- 신선도 게이트 없음: 오래된 항목도 항상 노출(사용자가 보고 정리). session-resume-notify 는 startup 에서만 발동(compact/resume/clear 제외).
- 순차 넘버링: ## Blockers 각 줄 맨 앞에 "N. " 순번을 붙인다(1부터, 등장 순서). 항목 추가/삭제 시 남은 항목을 1부터 재넘버링(구멍 없이). 텔레그램으로 태스크 목록을 보여주거나 사용자가 지시할 때도 항상 이 번호를 그대로 써서 사용자가 "1 진행해 3 잊어" 처럼 번호로 지목할 수 있게 한다. 모든 세션 공통 적용 — CLAUDE.md 가 심링크로 전세션 공유되므로 이 규칙도 전세션에 즉시 적용된다.  [R53]

## 라우팅 (quota 절약 모드 — 2026-07-13 ai-debate run-20260713T064600Z 개정)

/route의 목적은 자동 서브위임이 아니라 최소 quota 실행 경로 선택이다. 기본값은 inline. 구 루브릭("애매하면 서브", "파일 4개+/도구 5회+면 opus-sub", 자동 escalate-on-evidence)은 전부 폐기 — 전세션 opus 공유quota 체제에서 이게 비용 증폭기였다는 게 토론 결론.

- 즉답/소규모 수정/좁은 코드 탐색은 메인 세션에서 처리.
- 작업이 커지면 먼저 범위를 줄이고, 필요한 파일만 부분읽기하며, 긴 출력은 요약 — 이걸로 안 되면 그때 서브 고려(→ 위 "위임 규칙" 기준).
- sonnet-sub/opus-sub/haiku-sub는 사용자가 명시 요청했거나, 메인 컨텍스트 150k+ 폭발을 막기 위한 단일 격리조사일 때만. opus-sub가 기본 선택지였던 관행 폐기 — 고가치 검증이나 명시요청 없이는 쓰지 않는다.
- 작업 시작 전 관련 토픽 memory(memory/topics/<topic-id>.md, 없으면 MEMORY.md 인덱스)를 먼저 Read 해 맥락을 회수한다.
- 서브에이전트는 memory/progress/history 파일을 직접 write 금지. 표준 TOPIC-UPDATE 블록만 반환하고, 메인 세션만 반영한다(단일 writer).
- 사용자의 명시 오버라이드("이건 그냥 네가 해", "opus로 해", "빠르게")가 최우선.
